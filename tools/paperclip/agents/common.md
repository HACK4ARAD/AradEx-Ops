
## HACK4ARAD ground rules (all agents)
- Context: AradExperience for the Hack4Arad 2026 hackathon (7–8 Nov, code freeze Sunday 8 Nov 10:00, presentations 12:00). Team of 4 people, each owning one lane (see `docs/TEAM.md`); you are one of their AI teammates. Goal: a 6-minute demo with no major bugs, not perfect code.
- Where things run: every person runs their own Paperclip on their own laptop with their own Claude subscription. Persoana 1's Paperclip also hosts "Lead Tehnic" and "QA & Demo". The Paperclip instances do not talk to each other: **GitHub (`origin`) and `docs/STATUS.md` are the shared truth.** Never assume a task in your Paperclip is visible to the others.
- Repo: the folder of your Paperclip project's workspace (a clone of the team's GitHub repo https://github.com/HACK4ARAD/AradExperience; monorepo `api/` Spring Boot 3 + Java 21, `app/` Vue 3 PWA, `docs/`, `design/`, `tools/paperclip/`). Before any task read `CLAUDE.md`, the sub-folder `CLAUDE.md` you touch, your task section in `docs/PLAN.md`, `docs/API.md`, `docs/DATA-MODEL.md`, `docs/STATUS.md`, `docs/DEMO.md`. They win over anything generic here. Skills: `task-workflow` (start and finish every task with it), `be-module`, `fe-feature`, `seed-data` are attached to you as Paperclip skills; the same files live in `.claude/skills/` — if a skill is not available in your run, read its `SKILL.md` there and follow it.
- Every Paperclip task is titled `Txx: ...` and maps to one task in `docs/PLAN.md`. Stay inside that task; anything else goes to "De făcut mai târziu" in `docs/STATUS.md`.
- Git: start every task with `git fetch origin`. One task = one branch `feat/Txx-short-name` from `origin/main`, in a worktree next to the repo: `git worktree add ../_wt/Txx -b feat/Txx-name origin/main`. Never work in the main checkout; the human uses it. Small commits, short English messages (`feat(events): list + filters`). Never `git push --force` to shared branches, never push to `main` directly. When done: push the branch, open a PR with `gh pr create` (title `Txx: Summary`, body = what you tested and what not), put the PR link on the task.
- Cross-lane dependencies: before starting, check on GitHub that every task this one depends on is merged into `origin/main` (`git log origin/main --oneline`, `gh pr list --state merged`, `docs/STATUS.md`). If not, comment which one is missing, set the task to `blocked`, and stop. Do not re-implement another lane's work.
- Database: each worktree uses its own database so branches with different Flyway migrations never collide: create `aradexperience_txx` in the local Postgres 16 (`docker compose up -d` from the repo, or a local install) and run the API with `POSTGRES_URL=jdbc:postgresql://localhost:5432/aradexperience_txx`. Never edit a migration that is already on `main`; use the migration number reserved for your task in `docs/STATUS.md`.
- File ownership is strict (table "Cine ce atinge" in `docs/TEAM.md`): edit only your lane's backend packages, view files, components, `shared/api/<module>.ts`, `shared/types/<module>.ts`, `shared/i18n/ro|en/<module>.json`, your section of `docs/API.md`, and `docs/status/<your lane>.md`. Never edit `router/index.ts`, layouts/navigation, `SecurityConfig`, `Role`, shared `index.ts` barrels or `docs/STATUS.md` unless you are P1/Lead; import from module files directly. You may import and call other lanes' code (services, repositories, components, api modules); you may not edit it. If you need a change in another lane's file, ask for it on your task (blocked) instead of making it. Rebase on `origin/main` before opening the PR.
- Laptops are small: one heavy job at a time (Maven build, Vite build, API server). Stop servers you started before you finish the run. Never start two API instances.
- Verification is real: run `cd api && mvn test` (or `./mvnw test`) and `cd app && npm run build && npm run test`, then the "Verificare" checklist of the task (mobile 390×844 and web ≥1280 px). Do not disable tests to make them pass.
- UI text in Romanian with correct diacritics (ă â î ș ț), through i18n. Code, commits and PRs in English. Status comments on Paperclip tasks: short, in Romanian.
- Secrets: never read, print or commit `.env` values or keys (`OPENAI_API_KEY`, `JWT_SECRET`, Render/Netlify/Neon credentials). Only check whether a variable is set. The OpenAI key lives only in `api`.
- STOP and ask your human (comment on the task, set it to `blocked`, name what you need) before: creating accounts or projects on any external service, deploying anything, installing system software, spending money, sending any email/SMS/message to anyone outside the PR, adding a library outside the approved lists in `api/CLAUDE.md` / `app/CLAUDE.md`, or changing the demo flow in `docs/DEMO.md`.
- If something in PLAN/API cannot be done exactly, pick the simplest option that keeps the demo working, record it under "Decizii luate" in `docs/status/<your lane>.md` (in your PR), and move on.
- Done means: build + tests green, the task's "Verificare" checked, `docs/API.md` (your section) and `docs/status/<your lane>.md` updated in the PR, PR open with the link on the task, task set to `in_review`. QA & Demo (on Persoana 1's machine) reviews on GitHub and merges; when the PR has review comments, fix them on the same branch. The task is `done` only when the PR is merged.
