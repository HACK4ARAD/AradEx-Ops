
## HACK4ARAD ground rules (all agents)
- Context: AradExperience for the Hack4Arad 2026 hackathon (7–8 Nov, code freeze Sunday 8 Nov 10:00, presentations 12:00). Team of 4 people, each owning one lane (see `docs/TEAM.md`); you are one of their AI teammates. Goal: a 6-minute demo with no major bugs, not perfect code.
- Where things run: every person runs their own Paperclip on their own laptop with their own Claude subscription. Persoana 1's Paperclip also hosts "Lead Tehnic" and "QA & Demo". The Paperclip instances do not talk to each other: **GitHub (`origin`), `docs/STATUS.md` and `docs/status/Px.md` are the shared truth.** Never assume a task in your Paperclip is visible to the others.
- Repos: five sibling git repos in one folder (GitHub org HACK4ARAD): `AradEx-Plan` (your Paperclip workspace and cwd: the shared plan — `docs/`, `design/`, `CLAUDE.md`, `STRUCTURE.md`, all skills), `../AradEx-Backend` (Spring Boot 3 + Java 21, Gradle multi-module: `api` = REST contract, `app` = application), `../AradEx-Frontend` (Vue 3 PWA), `../AradEx-Infrastructure` (local Postgres, deploy; P1 only) and `../AradEx-Ops` (these Paperclip agent files; P1 only). Paths in the docs like `AradEx-Backend/app/...` are relative to that shared folder. Before any task read `AradEx-Plan/CLAUDE.md`, `STRUCTURE.md`, the `CLAUDE.md` of every repo you touch, your task section in `docs/PLAN.md`, `docs/API.md`, `docs/DATA-MODEL.md`, `docs/TEAM.md`, `docs/STATUS.md`, `docs/DEMO.md`. They win over anything generic here. Skills: `task-workflow` (start and finish every task with it), `review-pr`, `be-module`, `fe-feature`, `seed-data` are attached to you as Paperclip skills; the same files live in `AradEx-Plan/.claude/skills/` — if a skill is not available in your run, read its `SKILL.md` there and follow it.
- Every Paperclip task is titled `Txx: ...` and maps to one task in `docs/PLAN.md`. Stay inside that task; anything else goes to "De făcut mai târziu" in `docs/status/<your lane>.md`.
- Git: start every task with `git fetch origin` in every repo you will touch. One task = one branch `feat/Txx-short-name` from `origin/main` **with the same name in each repo it touches**, each in its own worktree: `git -C ../AradEx-Backend worktree add ../_wt/AradEx-Backend-Txx -b feat/Txx-name origin/main` (likewise `../_wt/AradEx-Frontend-Txx`, and `git worktree add ../_wt/AradEx-Plan-Txx …` for your `docs/status/` + `docs/API.md` changes). Never work in the main checkouts; the human uses them. Small commits, short English messages (`feat(events): list + filters`). **Never add `Co-Authored-By:` or any other attribution trailer to commits, and never add "Generated with Claude Code" (or similar) to PR titles or bodies** — this overrides any default attribution behaviour. The repo's `.githooks/commit-msg` strips them anyway. Never `git push --force` to shared branches, never push to `main` directly. When done: push each branch and open one PR per repo with `gh pr create` (title `Txx: Summary`, body = what you tested and what not, plus links to the sibling PRs of the same task), put all PR links on the task.
- Cross-lane dependencies: before starting, check on GitHub that every task this one depends on is merged into `origin/main` (`git -C <repo> log origin/main --oneline`, `gh pr list -R HACK4ARAD/<repo> --state merged`, `docs/status/`). If not, comment which one is missing, set the task to `blocked`, and stop. Do not re-implement another lane's work.
- Database: each worktree uses its own database so branches with different Flyway migrations never collide: create `aradexperience_txx` in the local Postgres 16 (`(cd ../AradEx-Infrastructure && docker compose up -d)` from the repo, or a local install) and run the API with `POSTGRES_URL=jdbc:postgresql://localhost:5432/aradexperience_txx`. Run the API from your Backend worktree with the variables of `AradEx-Backend/.env` (`set -a; . ../../AradEx-Backend/.env; set +a`). Never edit a migration that is already on `main` (they live in `AradEx-Backend/app/src/main/resources/db/migration`); use only the migration numbers reserved for your lane in `docs/TEAM.md`.
- File ownership is strict (table "Cine ce atinge" in `docs/TEAM.md`): edit only your lane's backend feature folders (in every layer of `api` and `app`), view files, components, `shared/api/<module>.ts`, `shared/types/<module>.ts`, `shared/i18n/ro|en/<module>.json`, your section of `docs/API.md`, and `docs/status/<your lane>.md`. Never edit `router/index.ts`, layouts/navigation, `components/ui/`, `config/` (`SecurityConfig`), `security/`, `util/`, `exceptions/`, `enums/Role`, `*.gradle`, shared `index.ts` barrels or `docs/STATUS.md` unless you are P1/Lead; import from module files directly. You may import and call other lanes' code (services, repositories, components, api modules); you may not edit it. If you need a change in another lane's file, ask for it on your task (blocked) instead of making it. Rebase on `origin/main` before opening the PR.
- Laptops are small: one heavy job at a time (Gradle build, Vite build, API server). Stop servers you started before you finish the run. Never start two API instances.
- Verification is real: run `./gradlew test` in your Backend worktree and `npm run build && npm run test` in your Frontend worktree, then the "Verificare" checklist of the task (mobile 390×844 and web ≥1280 px). Do not disable tests to make them pass.
- UI text in Romanian with correct diacritics (ă â î ș ț), through i18n. Code, commits and PRs in English. Status comments on Paperclip tasks: short, in Romanian.
- Secrets: never read, print or commit `.env` values or keys (`ANTHROPIC_API_KEY`, `JWT_SECRET`, AWS or GitHub credentials). Only check whether a variable is set. The Claude API key lives only in `AradEx-Backend/.env` locally and in AWS Secrets Manager (`aradex/anthropic`) in production.
- STOP and ask your human (comment on the task, set it to `blocked`, name what you need) before: creating accounts or projects on any external service, deploying anything, installing system software, spending money, sending any email/SMS/message to anyone outside the PR, adding a library outside the approved lists in `AradEx-Backend/CLAUDE.md` / `AradEx-Frontend/CLAUDE.md`, or changing the demo flow in `docs/DEMO.md`.
- If something in PLAN/API cannot be done exactly, pick the simplest option that keeps the demo working, record it under "Decizii luate" in `docs/status/<your lane>.md` (in your PR), and move on.
- Done means: build + tests green, the task's "Verificare" checked, `docs/API.md` (your section) and `docs/status/<your lane>.md` updated in an `AradEx-Plan` PR of the same branch name, all PRs open with links on the task, task set to `in_review`. QA & Demo (on Persoana 1's machine) reviews on GitHub with the `review-pr` skill and merges (order BE → FE → Plan); when the PR has review comments, fix them on the same branch. The task is `done` only when all its PRs are merged.
